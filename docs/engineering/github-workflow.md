# GitHub運用ルール

## 目的

このドキュメントは、TaskBoard リポジトリにおけるブランチ、コミット、Pull Request、マージ後作業の運用ルールを定義します。

変更履歴を追いやすくし、レビュー時に判断しやすい単位で作業を進めることを目的とします。

## 基本方針

- 作業は原則として `main` から作成した作業ブランチで行う
- 1つのブランチでは、1つの目的に集中する
- 無関係な変更を同じPRに含めない
- PR本文は日本語で記載する
- PRには動作確認、期待する結果、実行結果を記載する
- マージ後はローカルの `main` を最新化する

## ブランチ運用

### ブランチ作成

作業開始前に `main` を最新化し、作業内容に応じたブランチを作成してください。

```bash
git switch main
git fetch origin
git merge --ff-only origin/main
git switch -c <branch-name>
```

### ブランチ命名

ブランチ名は、作業種別と内容が分かる名前にしてください。

| 種別 | 用途 | 例 |
| --- | --- | --- |
| `docs/` | ドキュメント追加・修正 | `docs/add-github-workflow` |
| `chore/` | 設定、依存関係、検証コマンドなど | `chore/add-check-script` |
| `feat/` | ユーザー向け機能追加 | `feat/add-todo-form` |
| `fix/` | バグ修正 | `fix/prevent-empty-todo` |

既存ブランチの内容と現在の作業内容が合わない場合は、新しいブランチを作り直してください。

## コミット運用

### コミット単位

- レビューしやすい意味のある単位でコミットする
- 作業途中の不要なコミットを残さない
- フォーマット変更だけの差分と実装変更を不用意に混ぜない
- ユーザーが作成した未コミット変更を勝手に含めない

### コミットメッセージ

コミットメッセージは Conventional Commits を参考にし、次の形式を基本にしてください。

```text
<type>: <description>
```

必要に応じて scope を付けても構いません。

```text
<type>(<scope>): <description>
```

description は英語の命令形または簡潔な動詞句にしてください。
先頭は小文字にし、末尾のピリオドは付けません。

例:

```text
docs: add github workflow guide
docs: add todo feature spec
chore: add verify script
chore: install vitest
feat(todo): add todo form
fix(todo): prevent empty todo submission
```

よく使う type:

| type | 用途 |
| --- | --- |
| `docs` | ドキュメント変更 |
| `chore` | 設定、依存関係、検証ハーネスなど、プロダクトの振る舞いに直接影響しない変更 |
| `feat` | ユーザー向け機能追加 |
| `fix` | バグ修正 |
| `test` | テスト追加・修正 |
| `refactor` | 振る舞いを変えないコード整理 |
| `style` | フォーマットなど、動作に影響しない見た目上のコード修正 |
| `build` | ビルド設定や依存関係解決に関する変更 |
| `ci` | CI設定や自動化ワークフローの変更 |

破壊的変更がある場合は、`!` を付け、本文またはPR本文に影響範囲と移行方法を記載してください。

```text
feat(todo)!: change todo persistence model
```

このリポジトリでは、履歴を読みやすくするため、コミットメッセージ本文は必要な場合のみ使用します。
詳細な背景、動作確認、期待する結果、実行結果はPR本文に記載してください。

## Issue運用

### Issueを作成するタイミング

以下のような作業は、着手前に Issue を作成してください。

- 機能追加
- バグ修正
- 仕様の検討が必要な変更
- 複数PRに分ける可能性がある作業
- 後で対応する未決事項

小さなドキュメント修正や、作業内容が明確で1PRで完結する軽微な変更では、Issue作成を省略しても構いません。

### Issue本文

Issue本文は、次の形式を基本にしてください。

```md
## 概要
-

## 背景
-

## 対応内容
-

## 完了条件
-

## 補足
-
```

バグの場合は、再現手順と期待する結果、実際の結果を記載してください。

```md
## 再現手順
1. 
2. 
3. 

## 期待する結果
-

## 実際の結果
-
```

### Issueとブランチ

Issueに対応するブランチを作る場合は、可能であれば Issue 番号を含めてください。

```text
feat/12-add-todo-form
fix/18-prevent-empty-todo
docs/21-add-testing-guideline
```

Issue番号を含めない場合でも、ブランチ名から作業内容が分かるようにしてください。

### IssueとPR

PR本文には、関連する Issue を記載してください。

```md
## 関連Issue
- Closes #12
```

PRをマージしたら自動で Issue を閉じたい場合は、`Closes #<番号>`、`Fixes #<番号>`、`Resolves #<番号>` のいずれかを使ってください。

Issueを自動で閉じたくない場合は、次のように関連だけを記載してください。

```md
## 関連Issue
- Related to #12
```

### Issueの分割

Issueが大きくなりすぎた場合は、実装しやすい単位に分割してください。
1つのIssueに、複数の目的や独立した変更を詰め込みすぎないでください。

分割した場合は、元Issueに分割先のIssueまたはPRを記録してください。

## Pull Request運用

### PR作成前

PR作成前に以下を確認してください。

- 最終差分に無関係な変更が含まれていない
- 変更ファイルが作業目的と一致している
- 必要なドキュメントを更新している
- 必要なテストを追加または更新している
- 実行した検証と結果を説明できる

差分確認には、必要に応じて次を使ってください。

```bash
git status --short --branch
git diff --stat
git diff
```

### PR本文

PR本文は、次の形式を基本にしてください。

```md
## 実装内容
- 

## 変更した主要ファイル
- 

## 追加または更新したテスト
- 

## 動作確認
- 

## 期待する結果
- 

## 実行結果
- 

## 残っている問題
- 
```

### ドキュメントのみの変更

ドキュメントのみの変更では、`npm run verify` を省略しても構いません。
その場合は、PR本文の実行結果に未実行理由を記載してください。

例:

```text
`npm run verify` は未実行。ドキュメントのみの変更であり、アプリケーションの実行コードに変更がないためです。
```

### コード変更を含む場合

コード、設定、依存関係、検証ハーネスを変更した場合は、原則として次を実行してください。

```bash
npm run verify
```

実行できなかった場合は、理由と残るリスクをPR本文に記載してください。

## レビュー観点

レビューでは、最低限以下を確認してください。

- 要求された目的を満たしているか
- 変更範囲が過剰でないか
- 既存の設計方針やコーディング規約と矛盾していないか
- ユーザーから見える振る舞いの変更に対してテストがあるか
- PR本文の期待する結果と実行結果が対応しているか
- 未実行の検証がある場合、理由が妥当か

## マージ後の作業

PRをマージしたら、ローカルの `main` を最新化してください。

```bash
git switch main
git fetch origin
git merge --ff-only origin/main
```

作業ブランチが不要になった場合は、削除して構いません。

```bash
git branch -d <branch-name>
```

ただし、未マージの変更や確認が残っている場合は削除しないでください。

## やってはいけないこと

- `main` に直接コミットしない
- 無関係な変更を同じPRに含めない
- ユーザーの未コミット変更を勝手に戻さない
- 失敗した検証を成功したように記載しない
- install script を理由なく許可しない
- 破壊的な Git 操作を確認なしに実行しない
