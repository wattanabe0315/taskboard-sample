# コーディング規約

## 目的

このドキュメントは、TaskBoard のコードを読みやすく、変更しやすく、テストしやすい状態に保つための規約を定義します。

現時点では Next.js + TypeScript + React + Tailwind CSS を前提にします。
既存コードと矛盾する場合は、まず既存パターンを確認し、必要な差分だけを小さく変更してください。

## 基本方針

- 変更範囲は要求に必要な最小限にする
- 要求と無関係なリファクタリングを行わない
- 新しい抽象化を導入する前に、既存の配置・命名・責務分担を確認する
- ビジネスロジックを React コンポーネントに直接書きすぎない
- ユーザーから見える振る舞いを変更した場合は、テストを追加または更新する
- 依存パッケージは必要性が明確な場合のみ追加する

## TypeScript

- `strict` 前提で型を定義する
- `any` は原則使用しない
- 型エラーを避けるためだけの型アサーションは避ける
- 外部入力や将来変わり得る値は、必要に応じて境界で検証する
- 複数箇所で使う型は、責務に近い場所へ定義する
- React コンポーネントの props は明示的な型を定義する

例:

```ts
type TodoItemProps = {
  title: string;
  completed: boolean;
  onToggle: () => void;
};
```

## React / Next.js

- ページ固有の実装は `app/` 配下に置く
- `app/layout.tsx` には全体構造、フォント、グローバルCSS読み込みなど全ページ共通の責務だけを置く
- `app/page.tsx` にはルートページの画面構成を置く
- コンポーネントが大きくなった場合は、責務ごとに分割する
- TODOの状態遷移やバリデーションなどのビジネスルールは、可能な限り UI から分離する
- Next.js に関係する実装を変更する場合は、AGENTS.md の Next.js agent rules に従って `node_modules/next/dist/docs/` の該当ドキュメントを確認する

## ディレクトリ配置

現時点では `components/`、`domain/`、`tests/` は存在しません。
必要になった時点で、次の方針で追加してください。

```text
app/          Next.js のルーティングとページ
components/   再利用する UI コンポーネント
domain/       React に依存しないビジネスロジック
tests/        横断的なテストや fixture
```

対象コードの近くに置いた方が読みやすいテストは、同じディレクトリ付近に配置しても構いません。
どちらを選ぶ場合も、同種の既存パターンがあればそれを優先してください。

## 命名

- React コンポーネントは PascalCase にする
- 関数、変数、props は camelCase にする
- 型、interface、enum 相当の名前は PascalCase にする
- boolean は状態が分かる名前にする
- イベントハンドラは `handle` から始める
- props のコールバックは `on` から始める

例:

```ts
const isCompleted = true;

function handleSubmit() {
  // ...
}

type TodoFormProps = {
  onAddTodo: (title: string) => void;
};
```

## スタイリング

- Tailwind CSS の utility class を基本にする
- 同じ class 群が複数箇所に広がる場合は、コンポーネント化を検討する
- グローバルCSSには、全体で共有する CSS 変数や基本スタイルだけを置く
- コンポーネント固有の複雑な見た目を `app/globals.css` に集約しない
- レスポンシブ対応は、画面幅ごとの表示崩れが起きないように確認する

## 状態管理

- MVPでは、TODO状態はブラウザ上のメモリ管理を前提にする
- 状態更新は読みやすく、予測しやすい形にする
- 1つのコンポーネントに状態と操作が集中しすぎる場合は分割を検討する
- 永続化を追加する場合は、UIから直接ストレージや外部APIを呼び出さず、境界を分ける

## バリデーション

- TODO本文は追加前に前後の空白を削除する
- 空文字または空白だけのTODOは追加しない
- TODO本文は最大100文字とする
- バリデーションルールは、UI表示だけでなくテスト可能な形にする

## コメント

- コードを読めば分かる処理にコメントを付けすぎない
- コメントは「何をしているか」より「なぜ必要か」を優先する
- `scripts/verify.sh` などの検証ハーネスでは、各処理の目的を日本語コメントで記載する
- TODOコメントを残す場合は、後で判断できる具体的な内容にする

## テスト

- ユーザーから見える振る舞いを変更した場合は、テストを追加または更新する
- ドメインロジックは React から分離し、Vitest で単体テストしやすくする
- 外部API、現在時刻、乱数、ブラウザストレージに依存する処理は、テストで差し替えられるようにする
- 固定の sleep に依存するテストは避ける
- テスト観点は `docs/product/todo-app.md` も参照する

## 検証

通常は次を実行してください。

```bash
npm run verify
```

個別に確認する場合は、次を使ってください。

```bash
npm run lint
npm run typecheck
npm run test
```

ドキュメントのみの変更で `npm run verify` を実行しない場合は、PRに未実行理由を記載してください。

## PR前の確認

- 変更が要求に対して最小限か確認する
- `package.json` と `package-lock.json` に意図しない差分がないか確認する
- 依存パッケージを追加した場合は、追加理由と install script の有無を確認する
- ユーザーから見える振る舞いを変更した場合は、期待する結果と実行結果をPRに記載する
